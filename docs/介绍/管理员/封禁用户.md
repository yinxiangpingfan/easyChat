# 封禁用户 — BanUser

## 功能概述

管理员封禁指定用户，使其无法继续使用系统。封禁后，用户的现有会话会立即失效（删除 RefreshToken），且后续所有请求都会被认证中间件拦截。该接口采用 **数据库 + Redis + go-cache + Pub/Sub** 四层联动机制，确保封禁在分布式环境下即时生效。

## 路由信息

```
POST /v1/admin/banUser
```

中间件链：`TreaceLoggerMiddleware` → `AuthHttpMiddleware` → `CheckAdminMiddleware` → `BanUser Handler`

## 完整实现流程

### 1. 中间件鉴权阶段

与「获取用户列表」一致，依次经过 TraceLogger、Auth 认证、Admin 权限校验三个中间件。要求请求者必须携带有效的管理员 AccessToken。

### 2. Handler 层 — 参数绑定

从请求体中 JSON 绑定 `BanUserRequest` 结构体：

```go
type BanUserRequest struct {
    Uuid string `json:"uuid" binding:"required"`
}
```

绑定失败时返回 `400001 — 请求格式错误`。

### 3. Service 层 — 封禁执行（四步操作）

`adminServer.BanUser` 按顺序执行以下四个步骤，任一步骤失败均返回 `500001 — 系统繁忙` 并中止后续操作：

#### 步骤一：数据库状态更新

```go
repo.BanUser(ctx, uuid)
// 等价于: UPDATE user_info SET status = 1 WHERE uuid = ?
```

将 `user_info` 表的 `status` 字段从 `0`（正常）更新为 `1`（禁用），完成持久层的状态变更。

#### 步骤二：删除 RefreshToken

```go
redisClient.Del(ctx, "refreshToken:" + uuid)
```

从 Redis 中删除该用户的 RefreshToken。这意味着：
- 用户当前的 AccessToken（15 分钟有效期）到期后无法通过刷新获得新 Token
- 若用户恰好在此刻尝试刷新 Token，也会失败

#### 步骤三：写入 Redis 封禁标记

```go
redisClient.Set(ctx, "bannedUUID:" + uuid, "1", 0)
```

以 `bannedUUID:{uuid}` 为 key 写入 Redis，**永不过期**（TTL = 0）。Auth 中间件在 go-cache 未命中时会查询该 key 来判断用户是否被封禁。

#### 步骤四：Pub/Sub 广播封禁事件

```go
redisClient.Publish(ctx, "channel:user_ban", uuid)
```

通过 Redis Pub/Sub 机制向 `channel:user_ban` 频道发布封禁用户的 UUID。

### 4. Pub/Sub 订阅端 — 本地缓存同步

系统启动时会运行 `ListenToBanListChannel` 协程，持续监听 `channel:user_ban` 频道：

```go
func ListenToBanListChannel(cacheCache *cache.Cache, redisClient *redis.Client) {
    pubSub := redisClient.Subscribe(ctx, "channel:user_ban")
    for msg := range pubSub.Channel() {
        bannedId := msg.Payload
        cacheCache.Set(bannedId, "banned", 15*time.Minute)
    }
}
```

收到消息后，将该 UUID 在 go-cache 中标记为 `"banned"`（TTL 15min）。这样后续请求在 Auth 中间件的 L1 缓存层就能直接拦截，无需再查 Redis。

### 5. 封禁生效机制

封禁后，用户的请求会在 Auth 中间件中被拦截，具体流程：

```
用户请求 → Auth 中间件 → JWT 解析成功 → 封禁检查
  │
  ├── go-cache 命中 "banned"  →  直接拒绝 (400006)
  │
  └── go-cache 未命中
        │
        ├── Redis 查到 bannedUUID:{uuid}  →  写入 go-cache + 拒绝 (400006)
        │
        └── Redis 也没有  →  放行（不会出现，因为步骤三已写入）
```

返回错误码 `400006 — 用户已被禁用`。

## 核心设计

| 设计点 | 说明 |
|--------|------|
| 四层联动 | DB（持久化）→ Redis DEL（断会话）→ Redis SET（封禁标记）→ Pub/Sub（多实例同步） |
| 即时生效 | 删除 RefreshToken 阻止续签，Pub/Sub 同步本地缓存阻止当前 AccessToken 的请求 |
| 二级缓存拦截 | go-cache（L1, 15min）+ Redis（L2, 永久），减少封禁检查对 Redis 的频繁访问 |
| 永久封禁标记 | Redis 中的 `bannedUUID:` key TTL 为 0，只有解封操作才会移除 |
| 顺序执行 + 逐步回报 | 每一步失败都立即返回错误，避免部分成功导致状态不一致 |

## 调用链路图

```
Client (Admin)
  │
  ├── Authorization: Bearer <AdminAccessToken>
  ├── Body: { "uuid": "被封禁用户的UUID" }
  │
  ▼
TreaceLoggerMiddleware   →  生成 traceID
  │
  ▼
AuthHttpMiddleware       →  JWT 解析 + 管理员封禁检查
  │
  ▼
CheckAdminMiddleware     →  确认角色为 admin / superAdmin
  │
  ▼
AdminHandler.BanUser     →  ShouldBindJSON 绑定 uuid
  │
  ▼
AdminServer.BanUser      →  编排四步操作
  │
  ├── [1] repo.BanUser          →  UPDATE status = 1
  ├── [2] Redis DEL             →  删除 refreshToken:{uuid}
  ├── [3] Redis SET             →  写入 bannedUUID:{uuid} = "1"
  └── [4] Redis PUBLISH         →  channel:user_ban → uuid
                                       │
                                       ▼
                               ListenToBanListChannel (goroutine)
                                       │
                                       ▼
                               go-cache.Set(uuid, "banned", 15min)
  │
  ▼
JsonBack                 →  { code: 200, msg: "封禁用户成功", data: null, ret: 0 }
```

## 封禁状态在各存储层的体现

| 存储层 | Key | Value | TTL | 写入时机 |
|--------|-----|-------|-----|----------|
| MySQL (user_info) | uuid 行的 status 列 | `1` | — | 步骤一 |
| Redis | `refreshToken:{uuid}` | **已删除** | — | 步骤二 |
| Redis | `bannedUUID:{uuid}` | `"1"` | 永久 | 步骤三 |
| go-cache | `{uuid}` | `"banned"` | 15min | Pub/Sub 订阅端 |
