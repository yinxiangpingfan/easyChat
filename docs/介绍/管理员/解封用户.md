# 解封用户 — EnableUser

## 功能概述

管理员解除指定用户的封禁状态，恢复其正常使用权限。解封操作涉及 **数据库 + go-cache + Redis** 三层状态的同步更新，确保用户在解封后能立即正常登录和使用系统。

## 路由信息

```
POST /v1/admin/enableUser
```

中间件链：`TreaceLoggerMiddleware` → `AuthHttpMiddleware` → `CheckAdminMiddleware` → `EnableUser Handler`

## 完整实现流程

### 1. 中间件鉴权阶段

与「获取用户列表」和「封禁用户」一致，依次经过 TraceLogger、Auth 认证、Admin 权限校验三个中间件。要求请求者必须携带有效的管理员 AccessToken。

### 2. Handler 层 — 参数绑定

从请求体中 JSON 绑定 `EnableUserRequest` 结构体：

```go
type EnableUserRequest struct {
    UserID string `json:"user_id" binding:"required"`
}
```

绑定成功后，将 `req.UserID` 传递给 Service 层。绑定失败时返回 `400001 — 请求格式错误`。

### 3. Service 层 — 解封执行（三步操作）

`adminServer.EnableUser` 按顺序执行以下三个步骤：

#### 步骤一：数据库状态恢复

```go
repo.EnableUser(ctx, userID)
// 等价于: UPDATE user_info SET status = 0 WHERE uuid = ?
```

将 `user_info` 表的 `status` 字段从 `1`（禁用）更新回 `0`（正常），完成持久层的状态恢复。

若数据库操作返回 `gorm.ErrRecordNotFound`，返回 `500003 — 用户不存在`；其他错误返回 `500002 — 启用用户失败`。

#### 步骤二：更新本地缓存

```go
cacheCache.Set(userID, "normal", 1*time.Minute)
```

在 go-cache 中将该用户标记为 `"normal"`（TTL 1min）。这一步的作用是：
- **覆盖**之前由封禁流程写入的 `"banned"` 缓存值
- 使得该用户的后续请求在 Auth 中间件的 L1 缓存层直接被判定为正常用户并放行
- TTL 仅 1 分钟，之后自然过期，由正常请求流程重新回填

#### 步骤三：删除 Redis 封禁标记

```go
redisClient.Del(ctx, "bannedUUID:" + userID)
```

移除 Redis 中的永久封禁标记 `bannedUUID:{uuid}`。这一步确保：
- 当 go-cache 缓存过期后，Auth 中间件查询 Redis 也不会再误判用户为封禁状态
- 彻底清除封禁流程在 Redis 中留下的痕迹

### 4. 解封后的用户登录流程

解封后用户需要重新登录（因为封禁时 RefreshToken 已被删除），登录流程中：

```
用户登录 → 密码/验证码校验通过 → 生成新的 AccessToken + RefreshToken
  │
  ▼
后续请求 → Auth 中间件 → JWT 解析 → 封禁检查
  │
  ├── go-cache 命中 "normal"  →  直接放行
  │
  └── go-cache 未命中 → Redis 查 bannedUUID:{uuid}
        │
        └── 不存在（已删除）→  写入 go-cache "normal" + 放行
```

## 与封禁流程的对比

| 操作 | 封禁（BanUser） | 解封（EnableUser） |
|------|-----------------|-------------------|
| DB status | `0 → 1` | `1 → 0` |
| RefreshToken | Redis DEL 删除 | 不操作（用户需重新登录获取） |
| Redis 封禁标记 | SET `bannedUUID:{uuid}` = "1"（永久） | DEL `bannedUUID:{uuid}` |
| go-cache | Pub/Sub 写入 "banned"（15min） | 直接写入 "normal"（1min） |
| Pub/Sub 广播 | 发布到 channel:user_ban | 不广播 |

## 核心设计

| 设计点 | 说明 |
|--------|------|
| 三层状态同步 | DB（持久化恢复）→ go-cache（本地即时覆盖）→ Redis DEL（全局标记清除） |
| 主动覆盖缓存 | 不等待 go-cache 中 "banned" 自然过期，直接用 "normal" 覆盖，解封即时生效 |
| 短 TTL 缓存 | go-cache "normal" 仅 1 分钟，减少缓存与 DB 不一致的窗口 |
| 不广播解封事件 | 与封禁不同，解封未通过 Pub/Sub 广播；其他实例的 go-cache 中 "banned" 值将在 15 分钟内自然过期，之后查 Redis 即可得到正确状态 |
| 用户需重新登录 | 封禁时 RefreshToken 已被删除，解封不会恢复，用户必须重新走登录流程 |

## 调用链路图

```
Client (Admin)
  │
  ├── Authorization: Bearer <AdminAccessToken>
  ├── Body: { "user_id": "被解封用户的UUID" }
  │
  ▼
TreaceLoggerMiddleware   →  生成 traceID
  │
  ▼
AuthHttpMiddleware       →  JWT 解析 + 管理员封禁检查
  │
  ▼
CheckAdminMiddleware     →  确认角色为 admin / superAdmin
  │
  ▼
AdminHandler.EnableUser  →  ShouldBindJSON 绑定 user_id
  │
  ▼
AdminServer.EnableUser   →  编排三步操作
  │
  ├── [1] repo.EnableUser       →  UPDATE status = 0
  ├── [2] go-cache SET          →  uuid = "normal" (TTL 1min)
  └── [3] Redis DEL             →  删除 bannedUUID:{uuid}
  │
  ▼
JsonBack                 →  { code: 200, msg: "启用用户成功", data: null, ret: 0 }
```

## 解封后各存储层状态

| 存储层 | Key | Value | TTL | 说明 |
|--------|-----|-------|-----|------|
| MySQL (user_info) | uuid 行的 status 列 | `0` | — | 步骤一恢复 |
| go-cache | `{uuid}` | `"normal"` | 1min | 步骤二覆盖写入 |
| Redis | `bannedUUID:{uuid}` | **已删除** | — | 步骤三移除 |
| Redis | `refreshToken:{uuid}` | **仍不存在** | — | 需用户重新登录生成 |
